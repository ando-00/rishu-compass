# 監査

提出までに3回、リポジトリ全体を監査する。見るのは次の4つだけにする。

1. `AGENTS.md` の「守ること」が破られていないか
2. 判定が誤っていないか。誤るときは「職員確認」に倒れるか
3. 第三者が取得して、動かして、主張を確かめられるか
4. 使う人と審査する人に、価値と根拠が伝わるか

## いつ回すか

| 回 | 回す時点 | 遅くとも | 重点 |
|---|---|---|---|
| 第1回 | 正解ルールと判定エンジンのテストが揃ったとき | 11/5 | 判定の正しさ |
| 第2回 | Claude の連携が画面までつながったとき | 11/7 | Claude との境界 |
| 第2.5回 | 2026-11-02（人の決定で足した回） | 11/2 | 第1回と第2回の重点。判断不要の作業とフックを足したあとの全体 |
| 第3回 | 提出物が揃ったとき。作り手の依頼で 11/5 に回した | 11/8 12:00 | 再現性、提出要件。第3回の予行（11/3）の指摘が直っているか |

- 日付は目安とする。機能が遅れても第3回は動かさない
- 指摘がなくなるまで繰り返さない。回すのはこの3回と、人が決めて足した第2.5回だけにする。S1 を直したときは、その修正の再現テストで確かめ、監査全体はやり直さない
- 提出の直前と、リポジトリを公開する直前に、機械検査だけをもう一度回す
- 履歴を書き換えないため、一度入れた鍵や個人情報は消せない。push の前にも機械検査の鍵の3行を回す

## 毎回の手順

1. `docs/AUDIT_LOG.md` で前回の対象コミットと未解決の指摘を確認する
2. 機械検査とフォルダ構成の確認を回す
3. その回のサブエージェントを同時に起動する
4. 指摘を本体が再現し、重複をまとめて重大度を決める
5. 結果を `docs/AUDIT_LOG.md` に書き、`docs/PROGRESS.md` に1行足す

監査では直さない。修正は別の作業としてコミットする。直した指摘は、テストか機械検査に足して再発を防ぐ。

判定の根拠は実行結果とコードに置く。実行していない項目は合格にせず「未検証」と書く。

1回の監査は1時間までとする。第1回のあと、指摘を生まなかった検査は外すか軽くする。

## 体制

書いた本人の文脈を持たない目を入れるため、サブエージェントを使う。機械検査はコマンドで足りるので本体が回す。

| 回 | サブエージェント |
|---|---|
| 第1回 | ルール監査、コード監査 |
| 第2回 | ルール監査、コード監査、教務職員役 |
| 第2.5回 | ルール監査、コード監査、教務職員役 |
| 第3回 | ルール監査、コード監査、教務職員役、審査員役、初見の開発者 |

- 1つのエージェントに1つの観点だけを任せる
- 渡すのはコードと、この文書の該当の節だけにする。本体の見立て、作者の意図、前回の指摘は渡さない
- 読み取りだけを許す。修正とコミットをさせない。`gold*` を書き換えさせない。他の作品のフォルダを読ませない
- 指摘はそのまま記録しない。本体がテストかコマンドで再現し、再現できないものは「未確認」と書く
- サーバーへ要求を送る前に、待ち受けているプロセスが複製のものだと PID で確かめさせる。同じポートに別のセッションのサーバーがいることがある

## 重大度

| 区分 | 内容 | 対応 |
|---|---|---|
| S1 | 守ることの違反、誤判定、鍵や実データの流出 | 次の機能より先に直す |
| S2 | 提出や再現に支障がある | 提出までに直す |
| S3 | 改善 | 記録だけする |

## 機械検査

下のコマンドは `scripts/audit.mjs` にまとめてあり、何度でも同じ手順で回せる。Claude を呼ばず、作業ツリーを書き換えない。結果は `evals/tmp/audit/latest.md` に出る。

```bash
node scripts/audit.mjs          # 約1分。鍵、名前、依存の向き、作らないもの、履歴、フォルダ、build、test、CI
node scripts/audit.mjs --full   # 約30〜60分。上に加えて clean clone（.dev.vars なし）の ci/build/test、
                                # README の手順1〜10 のヘッドレスの Chromium での操作（scripts/e2e-readme.mjs）、
                                # 壊す検査、eval:recheck と eval:score の前回との比較、npm audit --omit=dev
```

`FAIL` があると終了コードが 1 になる。`未検証` は、名前の一覧がない、履歴が浅い clone、`gh` が使えない、など確かめられなかったものを示す。合格にはしない。

### 繰り返しの検査と、監査の回の違い

| | 繰り返しの検査 | 監査の回 |
|---|---|---|
| 中身 | `scripts/audit.mjs` とテスト | 下の「体制」のサブエージェント |
| 回数 | 何度でも。夜間ループは毎周回す | 3回だけ |
| 指摘の記録 | `FAIL` を直したら `docs/PROGRESS.md` に1行 | `docs/AUDIT_LOG.md` |

夜間ループの手順は `.claude/skills/night-loop/SKILL.md`、拾う作業は `docs/BACKLOG.md` にある。夜間ループは claude.ai のスケジュールで毎晩起動する。Claude Code の Stop フックが、作業を終える前に速い検査を回し、FAIL があれば終了を止めて直させる。

### コマンドの一覧

Git Bash で実行する。出力の期待値は各行の末尾に書いた。

```bash
# 鍵。AGENTS.md の説明文に一致しないよう、短い文字列は対象にしない
git grep -lE 'sk-ant-[A-Za-z0-9_-]{20,}' $(git rev-list --all)          # 空
git grep -nE --cached 'sk-ant-[A-Za-z0-9_-]{20,}'                       # 空
grep -rlE 'sk-ant-[A-Za-z0-9_-]{20,}|ANTHROPIC_API_KEY' dist/client     # 空

# 名前。一覧はリポジトリの外に置く
git grep -n -i -F -f ~/.claude/rishu-compass-denylist.txt               # 空
git log --format=%B | grep -n -i -F -f ~/.claude/rishu-compass-denylist.txt  # 空
git log --all --format='%an %ae %cn %ce' | grep -n -i -F -f ~/.claude/rishu-compass-denylist.txt  # 空。作成者欄
# 上の3つで、origin の GitHub のアカウント名の中だけの一致は数えない（clone の URL と作成者欄に必ず出るため。scripts/audit.mjs の N1、N2）
git log --all --format='%ae%n%ce' | sort -u                             # noreply@anthropic.com と <番号>+<名前>@users.noreply.github.com だけ（一覧がなくても回る。N3）

# 依存の向き
grep -rnE "from \"([^.]|\.\./\.\./)" engine --include=*.ts --exclude-dir=__tests__  # 空
grep -rnE "from \"(\.\./)+worker" src shared                            # 空

# 作らないもの
git grep -n "@anthropic-ai/sdk" -- ':!package.json' ':!package-lock.json' ':!docs' ':!scripts/audit.mjs'  # worker/ の中だけ
git grep -nEi "mailto:|send_email|nodemailer|resend|sendgrid" -- src worker shared engine wrangler.jsonc  # 空
git grep -nE "app\.(get|post|put|delete|patch|all)\(|\.route\(" -- worker ':!worker/__tests__'  # 全経路を読み、学生向けと送信がない

# 型の抜け道
git grep -nE '\bas any\b|: any\b|@ts-ignore|@ts-expect-error' -- '*.ts' '*.tsx'  # 空。あれば理由を読む

# 正解ルールと履歴
git grep -n "gold" -- src                                               # 空。画面から読まない
git grep -ln "gold" -- worker ':!*.test.ts'                             # worker/datasets.ts だけ
git log --format='%h %an | %(trailers:key=Co-Authored-By,valueonly)' -- 'data/fictional/*/gold*'  # 共著の表示がある。docs/DATA.md の経緯と合う
git log --format=%h -- data/fictional/sakuradai/handbook.md data/fictional/kamome/handbook.md data/fictional/advice-rules.md  # 46e408f だけ
git reflog | grep -E 'rebase|reset|amend' | grep -v 'reset: moving to HEAD$'  # 空（stash が残す記録は除く）
git merge-base --is-ancestor origin/main HEAD                           # 終了コード 0
git log --reverse --format=%aI | head -1                                # 開始時刻（2026-11-02T12:30+09:00）より後

# CI
gh run list --branch main --limit 1                                     # 最新の push が success
```

`scripts/audit.mjs` は、上のほかに次も回す。K3（コミットメッセージの鍵）、K5（`.dev.vars` が追跡されていない）、D3（engine、shared、worker が src を読まない）、X4（画面に相談チャットがない）、H3（push していないコミット）、H4（フックの場所）、F1〜F3（フォルダ構成）。

リポジトリの外に clean clone を作り、`.dev.vars` がない状態で `npm ci`、`npm run build`、`npm test` を通す。

名前の一覧には大学名、勤務先の略称、個人名、個人のメールを1行ずつ書く。GitHub のアカウント名は公開の識別子なので含めない。

## 守ることの確認

| 守ること | 確認すること |
|---|---|
| 計算に Claude を使わない | 単位、充足、検査、人数の値がすべて `engine/` の戻り値から来ている。Claude の応答の数値を画面や判定に使っていない |
| 検査に通らない案を出さない | 履修案が画面へ届く経路がすべて検査を通る。Claude に不正な案を返させるテストで、案が応答に含まれない |
| 未確定を確定にしない | 全ての曖昧箇所について、未回答なら関係する判定が「職員確認」になることを、1件ずつテストする。例外は、進級済みの学生の進級条件と、確定の区分に不足がある学生の卒業要件だけ |
| 特別な学生は全判定が職員確認 | 5種類の状態と適用外の入学年度の計6条件を、公開している全ての判定関数に掛け合わせてテストする。影響人数の集計でも同じになる |
| 声かけ文は下書き | 送信の経路がなく、画面でも下書きと分かる |
| 学生の画面とチャットを作らない | 経路と画面に学生向けと相談チャットがない |
| 架空データだけ | `data/fictional/` の外に大学のデータがない。追加したデータが `docs/DATA.md` と合う |
| 正解ルールは人が決める | 機械検査の結果に加え、`docs/DATA.md` の経緯と提出文が事実と合う。正解ルールの内容が要項の変換の入力と `dist/client` に入っていない。実行時のルールとして Worker が読み、対象が正解ルールのとき履修案の道具が判定の結果を Claude に渡すのは設計どおり |
| 既存コードを流用しない | 他の作品のフォルダは読まない。履歴を見て、説明のない大量の完成コードが1コミットで入っていないかを確認する |
| 進め方 | UI のステータスが色と文字の併記になっている。`docs/PROGRESS.md` が実際の作業と合う |

正解ルールが要項と違って見えても、監査では書き換えない。該当の条文と疑問点を記録し、人が判断する。

## コード監査

毎回、差分ではなく `engine/`、`shared/`、`worker/`、`src/` の全体を読む。動作に影響するものだけを指摘する。

- 同じ判定を2か所に書いていない。`worker/` や `src/` に判定の計算がない
- 失敗を握りつぶしていない。例外、空の配列、`undefined` が「問題なし」の判定にならない
- 表示の状態と engine の戻り値が1対1に対応している。想定外の値が緑の表示にならない
- テストの期待値がコードから写したものではなく、要項から手で求めたものになっている
- 残っている実装が今の仕様と合っている。使われていない分岐や古い説明がない
- `validateRuleSet` の検査をすり抜けた誤りが、実行時に黙って通るか止まるかを確認する。`dataset.problems` が唯一の防御線になっている

## テストの過不足

テストの件数やカバレッジ率では判断しない。誤りを入れたときに落ちるかで判断する。

```bash
# repo の外に engine、data、worker、shared、evals、src、migrations、vitest.config.ts、package.json をコピーし、
# node_modules へのジャンクションを張ってから実行する
node scripts/mutate.mjs <作業用コピーのパス>
```

結果の `SKIP` は、コードが変わって壊す箇所が見つからなかったものを示す。`scripts/mutate.mjs` の一覧を今のコードに合わせる。

| 種類 | 確認すること | 扱い |
|---|---|---|
| 不足 | 守ることに関わる箇所を壊してもテストが落ちない | S1 |
| 不足 | 要項の数値や境界に関わる箇所を壊してもテストが落ちない | S2 |
| 不足 | 並び順など、表示だけに関わる箇所 | S3 |
| 不足 | 見本にない形のルールでしか通らない分岐。`when` 付きの条件、複数の送り元、通年など | S2 |
| 過剰 | 同じ内容を別の場所で確かめているテスト | S3。実行時間が問題になるまで消さない |
| 誤り | 間違った動作を正しいものとして固定しているテスト | S1 または S2 |

壊す箇所が残っても、全部を埋めなくてよい。S1 と S2 だけを埋める。

## フォルダ構成の監査

毎回、本体が確認する。1回10分までとする。

- 最上位のフォルダが `AGENTS.md` の表と合う。表にないものには理由がある。`scripts/` は監査の道具を置く
- 中身が空のフォルダを残さない。git は空のフォルダを保存しないので、clean clone には存在しない
- 正解ルール、検査用ケース、評価結果の置き場が分かれている
- 生成物と秘密が `.gitignore` に入っている
- `evals/` のコードが型チェックとテストの対象に入っている
- 動かす場所を変えるだけの整理はしない。依存の向き、公開範囲、見つけやすさに影響するものだけを指摘する

## 立場を変えた評価

AI の役割による評価は、同じモデルの意見で、人の評価の代わりにはならない。点数は当てにせず、問題を見つけるために使う。

| 立場 | 渡すもの | 答えること |
|---|---|---|
| 教務職員役 | 動く画面。架空の業務シナリオ | 止まった箇所、根拠を信じられない箇所、誤って声をかけそうな箇所 |
| 審査員役 | README、提出文、デモ、公式の審査基準 | 3分で理解できない箇所。基準ごとの3段階と根拠 |
| 初見の開発者 | リポジトリの URL 相当の clean clone | README だけで動かしたときの手順の抜け |

- コードの説明ではなく、実際に画面を操作させる
- 作者の努力、自信のある箇所、期待する結論を伝えない
- 各自、重要なものを3件までに絞り、再現手順を付ける
- 点数を回の間で比べない。審査員役の3段階は、弱い基準を探すためだけに使う

提出前に、作り手以外の人には見せない。

## 回ごとの重点

### 第1回: 判定の正しさ

- 型で防げない参照切れを検査する。`ambiguityIds`、`patches` の `ruleId` と `field`、`overflowTo`、`groups`、科目名が実在するものを指す。`field` の書き間違いは何も変えずに通ってしまう
- `patches: []` の選択肢を選んだとき、回答済みの扱いが正しい
- `loadLimits` は条件に合う最後のものが使われる
- 仕様の境界を確認する。再履修、通年科目、集中講義、算入上限と超過分の振替、進級の判定年次
- 回答の前後で、影響人数が全学生の再計算の差と一致する。「職員確認」は人数を分けて示す
- 科目データにない科目が1人分あっても、全体の処理が止まらない。その学生が「職員確認」になる
- ルールが想定していない専攻の学生が「職員確認」になる
- 要項の全ての条文が、正解ルールの `clause` か、対象外の一覧のどちらかに載っている
- 選択肢の `patches` が空のとき、形式で表せない回答を確定として扱っていない
- かもめ大学の形のルールでも動く。`engine/` に特定の大学の科目名、区分名、単位数がない
- 仕様の T 番号がテスト名に入っていて、仕様との対応を追える。T19〜T24 の扱いを確認する

### 第2回: Claude との境界

- Claude の応答をすべて Zod で検証し、失敗したら内容を推測せずに失敗として示す
- 不正な形式、タイムアウト、レート制限、応答の打ち切りのテストがある
- 要項や職員の入力に命令文が混ざっても、判定と検査の結果が変わらない
- 必要な項目だけをプロンプトに渡している
- Claude を呼ぶ経路が `ALLOW_CLAUDE=true` を明示した環境でだけ動く
- 公開するのは `demo/` のブラウザの中で完結するデモだけで、サーバーを置かないので、配備の設定や公開時の防御は見ない。デモのビルドに API キーが入らないことは見る
- 回答者に実名を保存していない
- ログにプロンプト、応答の本文、学生の情報を残さない。`observability` が有効なので確認する
- API キーがブラウザへ渡らない
- 回答を変更または取り消すと、全ての判定が元に戻る
- 1回の操作と評価1周にかかる API の費用を把握している
- `.dev.vars` のない環境でも型チェックが通る。`wrangler types` は `.dev.vars` を読むため、手元と CI で `Env` が違う可能性がある
- `workers-best-practices` スキルの観点で `worker/` を確認する

### 第3回: 再現性と提出要件

- 公式の規定と FAQ を提出要件の一覧にして、1件ずつ確認する。一覧は人が用意する
- README の手順だけで、clean clone から起動できる
- README と提出文の主張を全てコードか評価結果で確認できる
- 評価の数値ごとに、結果ファイル、コミット、モデル ID をたどれる。都合の良い回だけを選んでいない
- `docs/DATA.md` が持ち込みデータと期間中に作ったデータを正しく分けている
- `docs/PROGRESS.md` に Claude Code の使い方が書かれている
- 架空の大学名が実在の大学と重ならないことを、公的な大学一覧で確認する
- デモを手元の環境で最初から最後まで通す。Claude の API が失敗したときの進め方を決めておく
- API キーなしで、README の手順が画面で最後まで通る
- `npm audit --omit=dev` の結果を確認する
- `dist/` を提出物に含めない。ビルドで `.dev.vars` がコピーされている
- リポジトリの公開の前に機械検査を回す。公開するかどうかは人が決める

## やらないこと

コードの書き方の好み、リファクタリングの提案、カバレッジの率、性能の改善、依存の更新、作らない機能の検討。これらは指摘にしない。動作やルールに影響するものだけを S3 までに記録する。

## 記録

`docs/AUDIT_LOG.md` に回ごとに次を書く。鍵の値と名前の一覧の中身は書かない。

```markdown
## 第N回 YYYY-MM-DD HH:MM

対象コミット: xxxxxxx
未検証: なし

| ID | 重大度 | 指摘 | 場所 | 状態 | 対応 |
|---|---|---|---|---|---|
| A1-1 | S1 | ... | engine/xxx.ts:12 | 解決 | コミット、追加したテスト |
```

## 実行のしかた

Claude Code に次のように依頼する。仕様文書はリポジトリにないので、場所を添える。

```text
docs/AUDIT.md に従って第N回の監査を実施してください。仕様文書: <パス>
```
